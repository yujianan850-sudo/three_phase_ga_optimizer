### DEF-1 🔴 `java_divide(x, y, 99)` 精度溢出（Ddyyn11 分支必然失败）

#### 现象

任何 `windingConnection = "Ddyyn11"` 的配置，在 Python 侧**整个搜索域 0% 可计算**，GA 完全无法启动。

实测（配置 369，6500 kVA）：

```
第 0 代全量覆盖 = 16430，可计算完整候选 = 0
恢复采样评价 = 19495，抽样尝试 = 20000/20000
终止原因 = initial_recovery_exhausted（初代恢复采样未找到两个可计算完整候选）
抽样 6000 条失败原因：6000/6000 全部「铁芯精算首段失败: [<class 'decimal.InvalidOperation'>]」
```

#### 定位

`calculation/single_device_evaluator.py:145`

```python
elif winding == "Ddyyn11":
    lp, plvn, hp, phvn = java_divide(p, TWO, 99), java_divide(lvn, SQRT3, 2), java_divide(p, TWO, 99), hvn
```

调用链（用 `sys.settrace` 抓取被 `except` 吞掉的原始异常）：

```
_phase_quantities()  第 145 行  java_divide(p, TWO, 99)
java_divide()        第  46 行  return scale(left / right, digits, rounding)
scale()              第  40 行  return value.quantize(Decimal("1").scaleb(-digits), rounding=rounding)
decimal.InvalidOperation
```

#### 根因

Python `decimal.quantize` 的结果**必须能装进当前上下文精度**（默认 `prec = 28`）。
`6500 / 2 = 3250`，量化到 **99 位小数**需要 `4 + 99 = 103` 位有效数字 ⇒ **必然溢出**。

实测（`p5_scale99.txt`）：

| 输入 | 99 位小数所需位数 | 结果 |
| --- | --- | --- |
| 0 | 100 | OK |
| 0.5 / 1 / 2 | 100 | **InvalidOperation** |
| 100 | 102 | **InvalidOperation** |
| 6500 | 103 | **InvalidOperation** |
| 123456 | 105 | **InvalidOperation** |

⇒ **除 0 以外，该调用一律失败**。不是数据问题、不是偶发。

#### Java 对照

`faladi_server/.../ThreePhase/impl/ThreePhaseSchemeRecordServiceImpl.java:886-890`

```java
case "Ddyyn11": //高压三角，低压星形
    LP = P.divide(BD_2);   // ← 无 scale、无 rounding，精确除法
    PLVN = LVN.divide(BD_SQRT_3, 2, RoundingMode.HALF_UP);
    HP = P.divide(BD_2);
    PHVN = HVN;
```

**Java 用的是不带 scale 的 `BigDecimal.divide(BD_2)`** —— 99 位精度是 Python 迁移时**自行加上**的，Java 原文里并不存在。`6500/2` 整除，Java 不会抛异常。

#### 影响面

| 项 | 值 |
| --- | --- |
| 涉及的 Ddyyn11 配置 | **10 个**：129 / 169 / 257 / 259 / 293 / 297 / 313 / 317 / 337 / **369** |
| 是否本轮引入 | **否** —— 09-19 冻结快照第 142 行同样存在 |
| 其中 9 个 | 先卡在 DEF-3（更早一层），只有 369 走到精算阶段而**暴露**了本缺陷 |

#### 修改方法

**方案 A（推荐，完全对齐 Java 语义）**

`calculation/single_device_evaluator.py:145` 改为：

```python
elif winding == "Ddyyn11":
    # Java: LP = P.divide(BD_2) 无 scale、无 rounding —— 精确除法；
    # 不引入 Python decimal 的 quantize 精度上限。
    lp = hp = p / TWO
    plvn = java_divide(lvn, SQRT3, 2)
    phvn = hvn
```

**方案 B（备选，保留"99 位"这个显然的笔误意图但使其可执行）**

在 `scale()` 内对超精度调用做保护：

```python
def scale(value: Decimal, digits: int, rounding: str = ROUND_HALF_UP) -> Decimal:
    exp = Decimal("1").scaleb(-digits)
    try:
        return value.quantize(exp, rounding=rounding)
    except decimal.InvalidOperation:
        with localcontext() as ctx:                     # 位数超过上下文精度时临时抬高
            ctx.prec = len(value.as_tuple().digits) + digits + 5
            return +value.quantize(exp, rounding=rounding)
```

> **推荐方案 A**：Java 原文就是精确除法，方案 B 会把一个 Java 侧不存在的精度要求固化下来，
> 且 `quantize` 到 99 位小数的结果在后续 `java_divide(..., 2)` 里同样会被重新量化，**99 位毫无意义**。

```java
BigDecimal paperCount = ThreePhaseCommon.calculateHVLN(layerVoltage, ratedVoltage);
if (paperCount.compareTo(BD_10) >= 0) {
    continue;                    // ← Java 语义：该高压层数候选不可用，跳过
}
markFlag(layerVoltagePassed);
candidates.add(new HighVoltageLayerCandidate(
    layer, decimalLayer, turnsPerSection, ThreePhaseCommon.calculateHVLT(paperCount.intValue())));
```

⇒ **Java 在 `paperCount >= 10` 时直接跳过该候选**（该"层数"根本不进入后续计算），
而 Python 把它当成"公式表缺失"抛 `ValueError`，并被 `evaluate()` 的 `except` 转成
「铁芯精算首段失败」，**语义错误且信息误导**。

#### 影响面

大容量 / 高电压等级配置（如 6500 kVA / 33 kV）中大量高压层数候选会落到 `paper_count >= 10`。
表现为「整域几乎不可计算」，实际是**这些候选本就不该存在**。

#### 修改方法

**方案 A（推荐，与 Java 完全一致：在高压候选阶段就排除）**

在 `_high_voltage_stage()` 计算完 `paper_count` 后，把「跳过候选」的语义显式化：

```python
paper_count = self._hvl_paper_count(layer_voltage, D(self.performance["highVoltageRated"]))
if paper_count >= 10:
    # 对齐 Java ThreePhaseSchemeRecordServiceImpl:337
    #   if (paperCount.compareTo(BD_10) >= 0) { continue; }
    # 该高压层数候选在本配置下不可用，不是公式表缺失。
    raise ValueError(f"高压层间纸档位 {paper_count} 已达 Java 上限 10，该层数候选不可用")
layer_insulation = self._hv_layer_insulation(paper_count)
```

并**同时**在域构造阶段排除这类层数（更彻底，避免反复精算浪费）：

`ga/gene_codec.py` 构造 `hv_layers` 域时，若能预判则直接剔除；
若不能预判（`paper_count` 依赖 `volts_per_turn`，需逐铁芯计算），则至少保证：

**方案 B（最小改动，仅修语义与信息）**

`_hv_layer_insulation` 的越界分支改为抛出**可识别的域拒绝异常**，并在 `evaluate()` 的
异常处理里把它映射成与 Java 一致的"候选不可用"诊断，而非"精算失败"。

> **建议**：先做方案 A 的**语义修正 + 诊断文案修正**（低风险），
> 域级预排除（性能优化）作为后续独立改动。

### DEF-3 🟠 油道字段只接受数组，Java 接受「标量或数组」

#### 现象

**143 个三相配置中有 68 个（47.6%）无法在 Python 侧构造搜索域**：

```
配置总数 = 143
Python 侧域构造成功 = 75
失败 = 68 —— 全部是「低压侧页面油道数量/类型不能为空」
```

#### 定位

`ga/gene_codec.py:210-218`

```python
@staticmethod
def _page_duct_options(craft: dict[str, Any], side: str) -> tuple[OilDuctScheme, ...]:
    counts, types = craft.get("channelCount"), craft.get("channelType")
    if not isinstance(counts, list) or not isinstance(types, list) or not counts or not types:
        raise ValueError(f"{side}侧页面油道数量/类型不能为空")
```

**仅接受非空 `list`**。

#### Java 对照

`faladi_server/.../entity/ThreePhase/jsonentity/ThreePhaseCraftLowCoil.java:23-33`

```java
/**
 * 低压油道数量，0-0无油道，1-一个油道，2-两个油道（支持多选数组，兼容历史单值 int）
 */
@JsonDeserialize(using = IntOrListDeserializer.class)
private List<Integer> channelCount = new ArrayList<>();

@JsonDeserialize(using = IntOrListDeserializer.class)
private List<Integer> channelType = new ArrayList<>();
```

Java 用 **`IntOrListDeserializer`** 明确兼容「标量 int」与「数组」两种历史格式；
Python 没有对应处理，直接判为缺失。

**数据库实测**（143 个配置）：

| 字段形态 | 配置数 |
| --- | ---: |
| LV `channelCount` 为 **list** | 75 |
| LV `channelCount` 为 **标量 int** | **68** |
| HV 同分布 | 75 / **68** |

受影响配置 ID（68 个）：
```

207 209 211 213 215 217 219 221 223 225 227 229 231 235 237 239 241 243 245 247
249 255 257 259 269 271 275 285 287 289 291 293 295 297 305 307 309 311 313 317
319 321 323 325 331 333 335 337
```

> 注：这批以 **Ddyyn11 / Yy / Yd** 接线与大容量配置为主（如 129/169/257/293/313/317/337 等）。

#### 修改方法

在 `_page_duct_options()` 入口做**标量归一化**（对齐 Java 的 `IntOrListDeserializer`）：

```python
@staticmethod
def _page_duct_options(craft: dict[str, Any], side: str) -> tuple[OilDuctScheme, ...]:
    """复刻 Java ``deduplicateChannelPairs``：页面数量×类型，多选笛卡尔积后归一化。

    count=0 或 type=0 都表示同一个 ``(0, 0)`` 无油道方案。

    Java 侧字段为 ``List<Integer>`` 并挂了 ``IntOrListDeserializer``，
    即**兼容历史单值 int 与多选数组两种格式**（见 ThreePhaseCraftLowCoil.java:26）。
    这里必须做同样的兼容，否则历史配置会被误判为"页面油道数量/类型不能为空"。
    """
    counts, types = craft.get("channelCount"), craft.get("channelType")
    counts = [counts] if isinstance(counts, (int, float)) else counts
    types = [types] if isinstance(types, (int, float)) else types
    if not isinstance(counts, list) or not isinstance(types, list) or not counts or not types:
        raise ValueError(f"{side}侧页面油道数量/类型不能为空")
    ...
```

> **建议**：`IntOrListDeserializer` 的语义等同 `[v] if isinstance(v, int) else v`，
> 建议在 `calculation/database.py` 的 `_decode_json_fields()` 之后**统一做一次字段归一化**，
> 这样 `channelCount` / `channelType` / 其它同类多选字段（若存在）一次性对齐，避免散落在各调用点。
