## 3. ❗ 核心发现：`java_divide(..., 99)` 是一个确定性代码缺陷

### 3.1 现象

对 369 的任意候选，`evaluate()` 都在同一处抛出 `decimal.InvalidOperation`，但被 `except` 吞掉，只留下 `铁芯精算首段失败`。用 `sys.settrace` 抓取被吞的原始异常，栈是：

```
_phase_quantities()  第 145 行
  lp, plvn, hp, phvn = java_divide(p, TWO, 99), ..., java_divide(p, TWO, 99), hvn
java_divide()        第 46 行
  return scale(left / right, digits, rounding)
scale()              第 40 行
  return value.quantize(Decimal("1").scaleb(-digits), rounding=rounding)
decimal.InvalidOperation
局部变量: {"left": "6500", "right": "2", "digits": "99", "rounding": "ROUND_HALF_UP"}
```

### 3.2 根因

Python `decimal` 的 `quantize` 结果必须能装进**当前上下文精度**。默认 `prec = 28`。
而 `6500 / 2 = 3250` 量化到 **99 位小数**需要 `4 + 99 = 103` 位有效数字 → **必然溢出**。

实测（`p5_scale99.txt`）：

| 输入 | 99 位小数所需位数 | 结果 |
| --- | --- | --- |
| 0 | 100 | OK |
| 0.5 / 1 / 2 | 100 | **InvalidOperation** |
| 100 | 102 | **InvalidOperation** |
| 6500 | 103 | **InvalidOperation** |
| 123456 | 105 | **InvalidOperation** |

⇒ **除 0 以外，该调用一律失败**。这不是数据问题、不是偶发，而是**该分支的确定性缺陷**。

### 3.3 与 Java 原文的偏差

Java 原文（`ThreePhaseSchemeRecordServiceImpl.java:886-890`）：

```java
case "Ddyyn11": //高压三角，低压星形
    LP = P.divide(BD_2);   // ← 无 scale、无 rounding，精确除法
    PLVN = LVN.divide(BD_SQRT_3, 2, RoundingMode.HALF_UP);
    HP = P.divide(BD_2);
    PHVN = HVN;
```

Java 用的是 `BigDecimal.divide(BD_2)`（**不带 scale**），`6500/2` 整除、不会抛 `ArithmeticException`。
Python 迁移却写成 `java_divide(p, TWO, 99)` —— **Java 原文里并不存在的 99 位精度要求**。

### 3.4 影响面

| 项 | 值 |
| --- | --- |
| 该缺陷存在的接线分支 | `windingConnection == "Ddyyn11"` |
| 全库 Ddyyn11 配置数 | **10 个**（129/169/257/259/293/297/313/317/337/369） |
| 冻结 zip（09-19）中是否已存在 | **是**（同在第 142 行）⇒ **非本轮引入，是长期存在** |
| Python 侧能否完成精算 | **不能**（`_phase_quantities` 是每次精算的必经路径） |

**10 个 Ddyyn11 配置中有 9 个首先卡在更早的一层**（`低压侧页面油道数量/类型不能为空`，属域构造阶段）；只有 369 走到了精算阶段，因此**暴露**了该缺陷。也就是说：**该缺陷的实际影响面 ≥ 10 个配置**，只是多数被更早的错误挡住而没显形。

### 3.5 修好它够吗？—— 不够，但缺陷是真实的

把 99 位分支改为精确除法（对齐 Java 语义）后，对 369 抽样 200 个候选（`p5_ddyyn11_after_fix.txt`）：

| 项 | 现状 | 仅修 99 位后 |
| --- | --- | --- |
| 可计算 | **0/200** | **0/200** |
| 首要失败原因 | `InvalidOperation` × 200 | `绕组高度无法对齐` × 79、`高压层间纸档位超出公式表: 10/13/15/11` × 41、`硅钢片缺少磁密损耗数据` × 6 |

⇒ 修好 99 位后**暴露出下面还有 2 层真实缺口**：
1. **高压层间纸档位溢出**：`_hv_layer_insulation` 的 `HVLT_N/M` 只有 10 档（index 0–9），但 6500 kVA / 33000 V 的 `paper_count` 会算到 10–15 → 索引越界。
2. **硅钢片磁密损耗数据缺口**：`27QG110` / `23ZDK90` 在部分磁密点（如 3.80/3.81）缺插值数据。

**因此本轮不能声称「Ddyyn11 修一行就能用」**，只能说：**99 位 quantize 是一个独立、确定、可复现的代码缺陷，必须在 Ddyyn11 可用之前修掉**；其后的两层缺口属**未完成的公式迁移范围**，需要另立项。

### 仍未覆盖 / 待修

1. **`java_divide(..., 99)` 缺陷未修** —— 影响全部 Ddyyn11 配置，本轮**只诊断未改码**（改公式须先确认）。
2. **Ddyyn11 的另外两层缺口**（层间纸档位表、硅钢磁密损耗数据）—— 属公式迁移未完成范围。
3. **9 个 Ddyyn11 配置的域构造失败**（`低压侧页面油道数量/类型不能为空`）—— 未单独定位，属独立问题。
4. **散热器 × 非 Dy 接线** —— 无可用样本，如实标注。

> **不得声称**：本轮**没有**修改任何源码；`java_divide(..., 99)` 的修复方案**已验证有效**（§3.5 通过 monkeypatch 证实），但**尚未落地**，须由用户确认后再改。
