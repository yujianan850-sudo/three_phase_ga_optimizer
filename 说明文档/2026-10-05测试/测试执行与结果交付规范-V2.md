## 1. 执行者先做这六件事

1. 阅读总计划§3、§4和本规范，确定测试负责人、代码版本、Python环境、数据快照及备份位置。正式运行前先解决缺项。
2. 核对并冻结统计方案，包括小样本/零差处理；准备新旧统计对照，不预设显著性结果。
3. 实现或补齐最小记录能力：初始完整序列、精算事件计数/阶段、逐候选约束、逐运行结果、压缩恢复校验。**不改变算法逻辑和原历史种子选择规则。**
4. 生成全部计划任务`jobs.jsonl`，先冒烟并通过输入一致、计数、导出和恢复检查；冒烟与正式批次分开保存。
5. 正式先执行P0的300个逻辑任务，核对差异；通过阶段门槛后执行P0_EXT的750个任务。每完成一条及时落盘，断点续跑不重写已经验收的结果。
6. 重算统计、生成机器可读图表源数据、复核候选、验证备份，完成报告和本规范§8验收表，再交给论文维护者。**不要只交截图、几张图或一段“全通过”的总结。**

### 执行入口要求

当前代码有`main.py ga-run`、`main.py ga-ablation`，但它们不等同于本规范的完整冻结输入/交付流程。执行者完成批次适配后必须提交：实际可执行命令、参数文件、脚本版本、工作目录、依赖安装/环境选择说明及恢复命令，写入`00_protocol/commands.md`。

## 4. 文件格式和标识约定

- JSON/JSONL使用UTF-8；JSONL每行一个合法对象；gzip解压后格式不变。金额、工程Decimal数值用十进制字符串，避免二进制浮点写回改变原值；统计量可用JSON number。
- 布尔值用true/false，未知或不适用用null并附原因；禁止NaN、Infinity、空字符串冒充0，也不能把失败成本写为0。
- 时间带时区，推荐ISO 8601 UTC；路径均相对结果包根目录。文件/候选规范化序列化规则写入manifest并固定，SHA-256使用64位十六进制。
- `logical_run_key = batch_role/config_id/method/seed`，预定P0与P0_EXT共1050个唯一键；`run_id`每次尝试唯一。`attempt`从1递增，重试用新run_id，保留`retry_of`和原因。
- `execution_status`用completed/error/interrupted/not_started；`strict_success`是另一个字段。正常结束但无严格解是completed+false，不是程序error。

### 4.1 manifest.json、jobs.jsonl及输入清单

manifest必须包含：schema_version、batch_id、created_at、负责人、protocol_version、protocol_sha256、批次角色、场景映射、全部seed、预期任务数、预算映射、实际Git commit、代码指纹及算法、source.patch哈希、Python可执行路径/版本、依赖版本、硬件/线程/并发、输入快照索引、统计方案哈希、运行/计时起止定义、初始序列规范化规则、抽查种子、重试规则和备份规则。

jobs每行包含：logical_run_key、batch_role、scene、config_id、method、strategy（默认为null）、seed、snapshot_id、settings文件路径/哈希、初始序列路径/哈希。必须在正式跑前生成并校验计数。

snapshot_manifest每个依赖文件包含：path、sha256、bytes、source、exported_at、role、config_id、is_original_20260924、旧版本证明或缺失说明。历史种子包含记录ID、来源、映射结果、排除原因；初始序列每行包含ordinal、candidate完整输入、candidate_key、source、source_metadata。同场景同seed的配对序列哈希必须一致。

### 4.2 run.json与summary.json

run.json必须包含：run_id、logical_run_key、batch_id、attempt、retry_of、scene/config_id/method/strategy/seed、snapshot_id/哈希、initial_sequence_sha256、实际完整settings、code_commit/指纹、实际命令、开始/结束时间、execution_status、产物相对路径。

summary.json必须包含下列字段；error/interrupted时尚未形成的结果可为null，error_details必须说明原因，不能伪造一条completed记录：

| 字段 | 含义/规则 |
|---|---|
| run_id、logical_run_key、execution_status | 与run.json一致 |
| strict_success、best_strict_cost | 成功与否；有严格解时成本为十进制字符串，无则null |
| best_strict_candidate_key、best_near_candidate_key、best_near_violation | 对应导出文件，缺失附原因 |
| initial_evaluations、evolution_evaluations、total_evaluations | evolution含第0代后的演化和末端细化，与旧口径对齐 |
| evolution_only_evaluations、refinement_evaluations | 分阶段计数，两者之和等于evolution_evaluations |
| cache_hits、generations_completed、termination_reason、budget_exhausted | 不用默认0掩盖未记录 |
| first_strict_total_call_index、first_strict_post_initial_call_index | 无解为null；第0代已成功时后者为0；还须保存candidate_key和phase |
| strict_count、near_count、archive_count_stage | 指明是工作代末还是末端细化后，不能混为图7指标 |
| wall_seconds、timing_scope | 时间起止、是否含初始化/IO，不将wall_seconds叫CPU时间 |
| error_details | 类型、消息、日志路径；正常运行可为null |

### 4.3 精算事件、候选与约束

evaluation_events每行至少含：run_id、event_seq（运行内单调唯一）、generation、phase（initial/evolution/refinement）、candidate_key、individual_id、source、cache_hit、evaluation_attempted、total_call_index、post_initial_call_index、calculable、complete、strict_feasible、cost、violation_sum、result_ref、error_ref、elapsed_seconds。

真实调用以实际精算器入口计数，不以插入一条individuals算一次。实际调用但报错也不能从调用预算中消失；缓存事件不增长调用序号，索引字段为null。合法化失败且未调用精算器要注明evaluation_attempted=false。每次真实调用恰好对应一个事件；其余内部状态日志单独记录，避免重复计数。若现有摘要使用不同口径，先报告差异、统一解释，不偷偷改算法。

best_strict/best_near非null时保存：candidate_key、完整candidate输入、完整result、来源individual_id/事件号、选择阶段、snapshot_id、价格及单位、所有必要工程指标。严格候选必须complete、calculable且有效硬约束全部满足；不是只凭汇总success标志。

selected_constraints每行含：run_id、candidate_key、constraint_name、unit、enabled、actual_value、lower、upper、rule_id、normalized_violation、passed、missing_reason。未配置边界不虚构限值；双边/单边及波纹补偿等特殊判据必须能回到冻结规则代码。所有候选的完整结果和约束可保存在SQLite中；不能只保留最终两条候选而丢掉过程。

### 4.4 统计和差异文件

- `primary_statistics.json`：逐场景n_expected/n_completed/n_missing，BGA/MGA成功数、b/c、原始p/Holm p、检验族ID；共同成功seed列表、配对数/零差数/非零差数、W+/W−、r_rb、Wilcoxon设置/警告/原始与校正p、HL绝对值及标准化值/CI/分母/bootstrap设置；全部成功成本n/min/Q1/median/Q3/max；调用量、停止原因和历史耗时描述。无法推断的字段用null并解释，不能填“不显著”代替数值缺失。
- `extension_statistics.json`：五场景每个变体的n与成功数；诊断扩展对去双档案的配对b/c、原始/校正p、检验族及方向定义。用E_EXT489，不用E487。
- `paired_costs.jsonl`：scene、seed、两run_id、两成本、差值MGA−BGA、是否零差、纳入原因，失败配对另在analysis_set标明。
- `all_success_costs.jsonl`：每次成功运行一条，含run_id/方法/seed/成本；不得冒充共同成功样本。
- `diversity_by_run.jsonl`：实际五字段、抽样候选标识及顺序、代、K、距离值、完整签名数、统计阶段；plot_data另外保存各方法共同覆盖代和30次聚合规则。无法重算的历史值明确标为历史值。
- `failure_by_run.jsonl`：失败run_id、所选最小超限候选、主导约束/超限值、并列破除顺序及类别。图8分母是失败运行，不是候选数。
- `old_new_comparison.jsonl`：每个逻辑任务每个字段一行，old_run_id/new_run_id、old_source/path/hash、field、old_value/new_value、comparison_rule、match、cause_status、cause_evidence；包含一致项，不仅保存差异。
- `replay_checks.jsonl`：抽查run_id/候选/选取规则与种子、冻结输入哈希、重算实现版本、原值/新值/容差规则、逐项pass、差异原因。抽查的成功/失败覆盖按总计划§6执行，纯同函数重调不能称独立外部验证。

所有plot_data记录源run_id或分析文件哈希、场景/方法、横纵坐标、单位、n、聚合与区间定义。不要只给四舍五入后的柱顶数字。

## 5. 失败、中断和重试怎么交

- 程序error/interrupted不是“算法没找到严格解”；完整记录后先查原因，不自动作为普通失败混入结果。
- 预先规定仅对基础设施错误等可解释原因重试；**正常无严格解不得为提高成功率重跑**。重试次数上限写入manifest，超限暂停，不无限重试。
- 同一logical_run_key保留所有attempt；analysis_set按冻结规则选择唯一有效完成run，填写selected_run_id、included、reason。若重试改变输入/代码/参数，不能算原任务续跑，须新批次并解释。
- 缺失任务仍列在jobs与analysis_set中；正式统计有缺失时标为incomplete，不用集合交集静默缩小n。中途报告必须写“阶段结果”。
- 发现新旧结论冲突，保留原始文件，写入差异清单；不得继续换seed或改预算直到复现旧数值。

## 6. 验证文件必须能回答什么

每个validation.json包括：run_id、文件非空、SQLite integrity_check原文、各关键表行数、数据库与摘要身份一致、真实调用计数对账、预算对账、初始序列哈希、候选/约束核对、原库SHA-256、压缩SHA-256、解压SHA-256、restore_pass、备份路径/时间/哈希、状态pass/fail/not_checked与失败原因。

最终acceptance.json至少列：P0预期300/实际完整/错误/缺失/重复；P0_EXT预期750及同类计数；1050个逻辑键的纳入状态；初始配对一致、每文件可解压、哈希与SQLite完整性、统计可重算、候选抽查、差异处置、脚本版本齐全等检查结果。检查缺失只能not_checked，不能默认pass。

从结果包另选一个干净目录执行恢复与分析，记录实际命令和日志；无需再访问在线业务库就能重算新批次表6/7/8/C1和图4—8源数据。需要在线库才能解释关键指标，视为输入或结果交付不完整。
