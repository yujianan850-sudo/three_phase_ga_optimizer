## DEF-3：油道字段兼容 Java 的历史单值

### 文件

`ga/gene_codec.py`

### 改动

**新增** `_normalize_multi_select()` 静态方法，并把 `_page_duct_options()` 由 `@staticmethod` 改为 `@classmethod`：

```python
@staticmethod
def _normalize_multi_select(value: Any) -> Any:
    """把 Java 兼容的历史单值还原成单元素列表。

    Java 的三相线圈实体把 ``channelCount`` / ``channelType`` 声明为 ``List<Integer>``，
    并挂了 ``IntOrListDeserializer``，即**同时接受历史标量 int 与多选数组**
    （见 ``ThreePhaseCraftLowCoil.java:26`` / ``ThreePhaseCraftHighCoil.java:26``）。
    数据库里这两种形态并存，Python 侧必须做同样的归一化，否则会把大量真实配置
    误判为"页面油道数量/类型不能为空"。非数值类型（字符串、None）原样返回，
    交给调用方按缺失处理。
    """
    if isinstance(value, bool):
        return value
    if isinstance(value, (int, float)):
        return [int(value)]
    return value

@classmethod
def _page_duct_options(cls, craft: dict[str, Any], side: str) -> tuple[OilDuctScheme, ...]:
    """..."""
    counts = cls._normalize_multi_select(craft.get("channelCount"))
    types = cls._normalize_multi_select(craft.get("channelType"))
    if not isinstance(counts, list) or not isinstance(types, list) or not counts or not types:
        raise ValueError(f"{side}侧页面油道数量/类型不能为空")
    ...
```

### 为什么这样改

| 依据 | 内容 |
| --- | --- |
| Java 实体 | `ThreePhaseCraftLowCoil.java:26` —— `@JsonDeserialize(using = IntOrListDeserializer.class)`，注释逐字：「支持多选数组，兼容历史单值 int」 |
| 数据实测 | 143 个配置中 **68 个**的 `channelCount` 是**标量 int**（另一半是数组） |
| 原行为 | 只认 `list` ⇒ 这 68 个配置全部抛「页面油道数量/类型不能为空」 |

**`bool` 被显式排除**：Python 里 `True` 是 `int` 的子类，若不排除会把布尔当数值处理。这里保持原样返回，仍按非法值走缺失分支。

## DEF-1：Ddyyn11 相电流改用精确除法

### 文件

`calculation/single_device_evaluator.py:153-161`

### 改动

```python
elif winding == "Ddyyn11":
    # Java: LP = P.divide(BD_2); HP = P.divide(BD_2); —— 不带 scale、不带
    # rounding，是精确除法（6500/2 整除，不会抛 ArithmeticException）。
    # 此处**不能**写成 java_divide(p, TWO, 99)：quantize 到 99 位小数需要
    # 103 位有效数字，而 decimal 默认上下文只有 28 位，必然抛
    # InvalidOperation，导致整个 Ddyyn11 配置 0% 可计算。
    lp, hp = p / TWO, p / TWO
    plvn, phvn = java_divide(lvn, SQRT3, 2), hvn
```

改动前：

```python
lp, plvn, hp, phvn = java_divide(p, TWO, 99), java_divide(lvn, SQRT3, 2), java_divide(p, TWO, 99), hvn
```

### 为什么这样改

| 依据 | 内容 |
| --- | --- |
| Java 原文 | `ThreePhaseSchemeRecordServiceImpl.java:887-890` —— `LP = P.divide(BD_2);` **无 scale、无 rounding** |
| 原行为的后果 | `quantize` 到 99 位小数需 **103 位**有效数字，默认 `prec=28` ⇒ **除 0 外必然** `InvalidOperation` |
| 影响面 | 全部 **10 个 Ddyyn11 配置** |

**为什么不用「抬高 decimal 精度」的方案**：Java 原文并没有 99 位的要求，那个 `99` 是迁移时写进去的；而且结果随后就会被 `java_divide(..., 1)` 重新量化到 1 位小数，99 位毫无意义。改精度只会把这个多余的约束固化下来。

### 验证

| 项 | 修改前 | 修改后 |
| --- | --- | --- |
| 369 抽样首要失败原因 | `[<class 'decimal.InvalidOperation'>]` × 200/200 | **不再是 InvalidOperation**（变为 DEF-2 的域规则拒绝） |

证据：`测试归档/2026-09-23测试/轨迹与运行输出/p5_ddyyn11_after_fix.txt`（修改前）、本轮实测（修改后）

## DEF-2：把「候选不可用」与「精算失败」分开

### 文件

`calculation/single_device_evaluator.py`

### 改动 1/3：新增异常类型（`:58-64`）

```python
class CandidateRejected(ValueError):
    """候选在本配置下**不可用**，不是公式链缺失，也不是程序缺陷。

    Java 主循环对这类情况一律 ``continue``（跳过该工作项，不进候选列表），
    因此 Python 侧必须把「候选被拒」与「首段精算失败」区分开：
    前者是正常的域内筛选结果，后者才代表迁移缺口或数据缺失。
    """
```

### 改动 2/3：两处"域规则拒绝"改抛 `CandidateRejected`

**高压层间纸档位**（`:337-340`）：

```python
if not 0 <= paper_count < len(values_n):
    raise CandidateRejected(
        f"高压层间纸档位 {paper_count} 已达 Java 表上限 {len(values_n)}，该高压层数候选不可用"
    )
```

**轭距对齐**（`:461-467`）：

```python
if high_yoke is None or low_yoke is None:
    # Java: ThreePhaseSchemeRecordServiceImpl:1335-1337
    #   BigDecimal[] calculationResult = findCrgoaAndYdd(...);
    #   if (calculationResult == null) { continue; }
    # 两侧轭距在 ±5 内无法对齐时 Java 直接跳过该工作项。
    raise CandidateRejected("绕组高度无法在 Java 规定的轭距 ±5 范围内对齐，该候选不可用")
```

### 改动 3/3：`evaluate()` 增加专属 except 分支（`:1455-1461`）

```python
except CandidateRejected as exc:
    # Java 主循环对这类候选一律 continue：它在本配置下**不可用**，
    # 既不是迁移缺口也不是数据缺失，因此不得与"首段精算失败"混淆。
    return EvaluationResult(
        complete=False, calculable=False, feasible=False,
        diagnostic=[f"候选被域规则拒绝: {exc}"],
    )
except (ArithmeticError, KeyError, ValueError, NotImplementedError) as exc:
    return EvaluationResult(
        complete=False, calculable=False, feasible=False,
        diagnostic=[f"铁芯精算首段失败: {exc}"],
    )
```

> **`except` 顺序很关键**：`CandidateRejected` 继承 `ValueError`，**必须排在父类之前**，
> 否则会被后面的宽泛分支吃掉。

### 为什么这样改

| 依据 | 内容 |
| --- | --- |
| Java 纸档位 | `ThreePhaseSchemeRecordServiceImpl.java:336-339` —— `if (paperCount.compareTo(BD_10) >= 0) { continue; }` |
| Java 轭距 | `ThreePhaseSchemeRecordServiceImpl.java:1335-1337` —— `if (calculationResult == null) { continue; }` |
| 原行为的误导 | 两者都抛 `ValueError`，被 `except` 统一写成「**铁芯精算首段失败**」—— 让人误以为公式链有缺口或数据缺失，实际是**该候选本就不该存在** |

### 验证

369 抽样 200 条，诊断文案由「铁芯精算首段失败」变为**可区分的两类**：

| 诊断 | 条数 | 性质 |
| --- | ---: | --- |
| `候选被域规则拒绝: 绕组高度无法…对齐，该候选不可用` | 79 | 域规则 |
| `候选被域规则拒绝: 高压层间纸档位 10/11/13/15 已达 Java 表上限 10` | 41 | 域规则 |
| `铁芯精算首段失败: 硅钢片 27QG110 缺少磁密 3.80/3.81 的损耗数据` | 6 | **真实数据缺口** |

⇒ 剩余的**真实迁移缺口被凸显出来**（6/200），不再与域规则混在一起。

⇒ **Ddyyn11 的公式链仍有实质性缺口**，不是"随机撞到不可行组合"。

**已排查并排除的一个假设**：

疑点：Java 的 `ddyyn11Add` 取 `cache.LVSD`，而 `ThreePhaseCommon.java:1578` 显示
`this.LVSD = config.getPerformanceIndex().getLowVoltageSectionSpacing()`（= **60**）；
Python 的 `split_height_add` 读的是 `craft_low_coil.lowVoltageSectionSpacing`（= **None → 0**），
**取值来源不一致**。

实测（把 Python 改成读 `performance_index` 后重抽样 60 个候选，`369`）：

| 方案 | 可计算 | 首要失败 |
| --- | ---: | --- |
| A. 现状（读 `craft_low_coil`） | **0/60** | 轭距无法对齐 ×21 |
| B. 假设修复（读 `performance_index`=60） | **0/60** | 轭距无法对齐 ×21 |

⇒ **该不一致存在，但不是当前 0% 可计算的原因**（两者失败分布完全一致）。
真正原因是 Python 缺少 Java `ConfigCache` 里的 **`adjustLVRHMIN/MAX` 一类预过滤**
（见 `ThreePhaseSchemeRecordServiceImpl.java:3253-3262`：Java 在进主循环前就用
`(LVRHMIN - LVSD) / (LVAPN × 2)` 把低压线宽范围收窄了）。**该项未修**。

> **性质**：这两条都属于**公式迁移未完成**，不是本次改动引入的缺陷，需另立项。
> 本次改动把它们从"被 `InvalidOperation` 掩盖"变成"**可观察、可区分**"，是修复的前置条件。
