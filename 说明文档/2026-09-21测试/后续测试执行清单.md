## 1. 先统一测试口径

### 1.1 三类测试分别回答什么

| 测试类别 | 要验证的结论 | 可以得出的结论 | 不能得出的结论 |
| --- | --- | --- | --- |
| 单设备一致性 | 同一条方案、同一份输入下，Python 是否复现 Java 当前计算结果 | 被测字段和被测分支的差异已记录或已解释 | 所有产品、全部工程分支均已验证 |
| 功能与页面回归 | 搜索域、算子、轨迹、页面交互是否按设计执行 | 指定输入下的功能行为正确或存在缺陷 | 某种 GA 策略一定更优 |
| 多种子效果实验 | 在同一任务和公平计算口径下，新策略是否改善可行性或成本 | 本配置、本搜索域和本预算下的统计结果 | 对所有产品的普遍最优性结论 |

### 1.2 统一术语

- **严格合格**：`calculable=True`、`complete=True` 且 `feasible=True`。只有这类候选计入严格可行率和严格成本比较。
- **近可行**：能够完整计算，但至少一项约束超限。它可以用于搜索过程和“最小超限”指标，不能写成已满足设计要求。
- **第 0 代成本**：多背景 A/B 覆盖、历史种子和随机补足的精算调用数。
- **演化成本**：第 0 代之后，交叉、变异、注入和局部探测等产生的真实精算调用数。
- **预算 B**：所有阶段的真实精算调用安全上限，仅用于实验或小预算回归；日常页面运行和普通 `ga-run` 不需要设置。
- **演化预算 B′**：第 0 代完成后才开始计数的真实精算调用上限，只用于同配置、同搜索域、同批种子之间的公平策略比较。不同产品配置不应用同一个 B′ 直接比较“谁更难”。

### 1.3 每次测试都要保存的共同信息

每个测试样本或每次 GA 运行至少保存以下内容：

| 内容 | 要求 |
| --- | --- |
| 测试时间与程序版本 | 记录测试时间、当前提交/压缩包版本或关键文件修改时间。 |
| 输入标识 | 三相配置 ID、Java 方案记录 ID（如有）、随机种子（GA 时必填）。 |
| 搜索域 | 硅钢、铁芯形状、两侧导线类别、冷却形式、波纹面数/散热器片宽与组数、整数范围。 |
| Java 证据 | 经 `faladi_mcp` 请求的时间、接口结果或保存快照；不能只引用很早的页面截图。 |
| Python 证据 | 页面截图、终端输出或对应 SQLite 路径；发生异常时保留完整报错。 |
| 人工结论 | 明确写“通过 / 不通过 / 无法判断”，并解释依据。 |

业务数据库始终只读。测试 SQLite 必须保留到结论确认；不应与正式实验轨迹混放或重命名为正式结论文件。

## 2. 单设备精算一致性回归

### 2.1 待验证结论

1. 对同一条已保存 Java 方案，Python 能还原相同的铁芯、导线、匝数、层数、油道和冷却结构。
2. 在相同输入和价格来源下，Python 的电气、几何、热工、重量和成本字段与 Java 当前计算结果一致，或差异能够被明确归因。
3. Python 约束诊断的上下限、当前值与 Java 计算结果没有因输入还原或公式差异而产生错误判定。
4. 波纹油箱与散热器油箱、圆形/长圆/椭圆铁芯的已实现分支均至少有真实样本验证。

### 2.2 单条样本如何测试

对每条样本按以下顺序操作：

1. 选定 Java 已保存方案记录，记录配置 ID 和记录 ID。
2. 通过 `faladi_mcp` 按其封装的后端流程请求该方案的最新计算或快照；保存请求时间和返回结果。不要直接用旧页面显示值替代该步骤。
3. 打开 Python 页面：`单设备精算 → 设置本次搜索范围`。确保本条方案所需的硅钢、铁芯形状、低压/高压导线类别和冷却形式都被包含。
4. 进入 `选择方案并复算`，选择同一 Java 记录。确认回填后的完整记录 ID、类别、匝数、层数、油道和冷却结构与 Java 一致；如需手动修改，仅用于定位问题，并在报告中明确写出修改项。
5. 点击精算，转到 `查看计算结果`，保存指标和中文约束诊断。
6. 再进入 `一致性验证 → 字段对比`，选择同一记录并执行比较；保存表格。
7. 填写本清单第 7 节的单设备测试报告表。

### 2.3 最低样本覆盖矩阵

不要求一个样本覆盖所有维度；应选多条真实方案拼成覆盖矩阵。每一格至少有一个可比较的真实样本，找不到时必须在报告标记“当前无样本”，不能用虚构数据补齐。

| 维度 | 最低覆盖 |
| --- | --- |
| 铁芯形状 | 圆形、长圆、椭圆各至少一条；长圆样本必须记录 `conversionC`。 |
| 油箱/冷却 | 波纹油箱、散热器油箱各至少一条。 |
| 低压导线 | 箔材、扁线各至少一条。 |
| 高压导线 | 圆线、扁线各至少一条；若数据库中有 QQL/QQLB 等不同类别，应至少各取一条。 |
| 油道 | 低压、高压均至少覆盖两种真实的“数量 + 半/全油道”组合。 |
| 约束边界 | 尽量覆盖接近或触发 P0、PK、UK、绕组高度、温升、波纹补偿/散热器中心距的样本。 |
| 价格来源 | 至少一条方案配置价格完整的样本；若存在真实缺价方案，再增加一条走 MCP 补价的样本。 |

### 2.4 每条样本必须核对的字段

| 类别 | 至少记录的字段 |
| --- | --- |
| 输入还原 | 硅钢、铁芯 ID/形状/直径、低高压导线类别和记录 ID、低压匝数、两侧层数、两侧油道、冷却型号、`conversionC`、价格来源。 |
| 电气 | 磁密 CT、P0、PK、UK。 |
| 几何与热工 | 低高压绕组高度、油顶温升、低压温升、高压温升；波纹补偿量或散热器中心距。 |
| 重量与成本 | 油重、油箱及散热部件重量、总装配重量、可获得的价格分项、总成本。 |
| 约束 | 中文约束名称、下限、上限、Java 当前值、Python 当前值、差值及两端判定。 |

不设一个脱离字段精度的人工“允许误差”。报告应按 Java 实际保存精度比较；若存在非零差异，必须标明是显示舍入、Java 未保存快照、价格输入不同、候选还原不同，还是疑似公式差异。只有前四类均排除后，才归为 Python 公式问题。

### 2.5 通过与后续处理

- **通过**：输入一致；每一个可比较字段一致，或差异已有可复核且不改变结论的解释；约束判定一致。
- **不通过**：候选无法还原、关键字段差异无法解释、约束判定不同，或 Python 使用了错误的价格/冷却/油道输入。
- **无法判断**：Java 未保存字段、后端请求未完成或样本缺少必要目录记录。它不是“通过”。

若不通过，报告需附 Java 快照、Python 结果、候选编码和复现步骤；维护方先定位输入还原、价格来源、保存字段或公式分支，再修改。修复后必须回归所有此前通过的代表样本，而不是只重测失败样本。

## 3. 搜索域与第 0 代测试

### 3.1 待验证结论

1. 页面所选研究边界实际传入 GA，而非只改变显示。
2. 线规始终是“导线类别 + 完整记录 ID”；不会生成不存在的宽厚组合。
3. 低压层数遵循导线类别规则；高压层数和低压匝数来自 Java 页面范围。
4. 波纹长短轴面数、散热器片宽和组数进入冷却候选域；候选不会把波纹和散热器部件混装。
5. 第 0 代轨迹真实记录 A/B 覆盖、历史种子、随机补足和精算结果。
6. 第 0 代的不可计算或结果不完整候选保留覆盖证据与失败诊断，但不会进入第 1 代父代池；工作种群只由可计算完整候选组成。
7. 原始第 0 代可计算完整候选不足两条时，系统只在同一页面允许域内补抽未见完整组合；找到两条后才能开始遗传迭代，达到自动恢复上限仍不足时必须正常终止并完整写入原因。

### 3.2 如何测试

1. 选择一个目录中同时存在多种铁芯、低高压线规和两种冷却形式的配置。
2. 在“设置本次搜索范围”中故意缩小边界：保留少量硅钢、一个或两个铁芯形状、指定的低高压导线类别；同时给出至少两个波纹面数组合或散热器组数/片宽组合。
3. 在 `GA 优化实验 → 第 0 代准备` 展开覆盖计划，截图保存整数来源、允许值和 A/B 计划。
4. 运行“生成第 0 代并写入本地轨迹”。
5. 在“轨迹回放”加载该 `initial-preview` 文件，检查候选结构、来源汇总和候选结果。
6. 再将边界改为另一组明显不同的值，重复一次，比较两份轨迹是否确实只含各自允许范围内的候选。

### 3.3 报告必须回答的问题

- 两次边界分别是什么；各域实际候选数量是多少；
- 轨迹是否出现被排除的铁芯、导线类别/记录、冷却形式或冷却参数；
- 每种允许导线类别是否以完整记录出现，是否观察到任何“宽取 A、厚取 B”的虚构规格；
- 低压箔材的层数是否等于本候选低压匝数，扁线是否只取 2 或 4；
- 高压层数、低压匝数的最小值、最大值和步长是否与 Java 页面一致；
- 第 0 代来源汇总、不可计算原因和 SQLite 路径。
- 第 0 代全量候选数、可计算完整候选数、实际工作种群数；随机抽查工作种群候选，确认其 `calculable=True`、`complete=True`。
- 若触发恢复采样：原始可计算完整数、恢复评价数、抽样尝试数/自动上限、恢复候选是否仍在页面允许域内、最终是否达到两条不同可计算候选；若未达到，是否留下 `initial_recovery_exhausted` 终止记录与中文原因。

出现任何被排除值、虚构规格、错误层数或错误整数边界，即为不通过，应附对应候选 ID 和轨迹文件。

## 4. GA 运行与算子功能回归

### 4.1 当前仍需验证的结论

1. 页面运行时的第 0 代进度、GA 实时状态和最终档案与实际轨迹一致。
2. 结构电磁耦合交叉、探索性交叉、经验有效域注入、普通随机变异和诊断反馈变异的设置确实改变实际候选来源，而非仅改变页面标签。
3. 阻抗定向变异按违规方向优先调整单侧油道：UK 偏高优先尝试更少/更小的合法油道，UK 偏低优先尝试更多/更大的合法油道；每一侧先只试距离当前值最近的同向合法档位，不能在首轮 probe 中跨多个档位深跳；没有同向合法油道邻居时必须回退普通随机变异，不能用铁芯邻居凑 probe，也不能虚构油道方案。
4. 精英复制、缓存命中、普通创建和局部探测在轨迹中的语义可区分；进入定向变异前的基体必须显示为 `guided_mutation_base`，其前序交叉类型只可作为补充来源信息，不能伪装为本次创建动作。
5. 页面策略下拉、`ga-run --experiment-strategy` 与 `ga-ablation` 对同名策略生成相同的实际 settings；每份新轨迹都包含公式版本、核心代码指纹、运行入口、实际策略和耗时。

### 4.2 如何测试页面运行与轨迹

1. 使用一个第 0 代规模足够大、运行至少两代的真实配置；记录页面设置、随机种子和页面研究边界。
2. 启动 GA 后，在第 0 代和至少一代完成后各截图一次：页面进度、实际精算调用、缓存命中、严格档案数、近可行档案数和前五名。
3. 运行中切换到另一个一级页面后再返回，确认“最近一次 GA 运行状态”显示的是最后一次真实快照，而不是归零或伪造完成。
4. 运行完成后加载对应 SQLite，比较最终页面数字与轨迹中的代数、调用数、档案数量、停止原因是否一致。
5. 在轨迹的“候选与演化关系”中各找至少一条精英、缓存命中、交叉/变异和局部探测候选，保存其中文来源、父代、本代去向、档案归属和入档前最后动作。
6. 分别以页面和 `ga-run --experiment-strategy guided_mutation` 运行同一小范围输入；再以 `ga-ablation` 读取同一策略。核对三者的耦合交叉比例、注入模式和定向变异模式相同，并核对轨迹设置包含公式版本、核心代码指纹、入口、策略和非负耗时。

### 4.3 如何测试阻抗定向变异

这项不能仅凭代码阅读宣称通过。应从真实运行轨迹中分别寻找至少一个 UK 偏高和一个 UK 偏低的、触发诊断反馈变异的近可行父体；若当前配置没有此类样本，应记录“未覆盖”，再换配置或搜索域。

对每个样本检查：

| 检查项 | UK 偏高时预期 | UK 偏低时预期 |
| --- | --- | --- |
| 轨迹诊断 | `primary_module=radial_duct`，记录 `violation_direction` | 同左 |
| 优先探测 | 高压或低压一侧油道向更少/更小的**最近**页面允许方案变化 | 高压或低压一侧油道向更多/更大的**最近**页面允许方案变化 |
| 禁止行为 | 不改变另一侧油道，不生成页面外的数量或类型 | 同左 |
| 油道不足时 | 不生成阻抗局部 probe，回退普通随机变异 | 同左 |
| 结果判定 | 每个探测候选均有重新精算结果；是否改善由真实超限决定 | 同左 |

报告不要只截取“成功改善”的候选。应同时给出本次命中的所有阻抗定向探测数量、改善数、未改善数、无油道邻居的随机回退数，以及每条探测的前后油道、UK、总超限和是否进入下一代/档案。若当前为“2 个全油道”，且同侧允许“1 个全油道”和“无油道”，首轮必须先出现“2 全 → 1 全”，不得直接把“2 全 → 无”当作同侧最近 probe。

### 4.4 负载损耗线规方向回归

从真实运行轨迹中找至少一个 `load_loss/upper` 和一个 `load_loss/lower` 的定向变异基体；没有样本时应记录未覆盖，不可用人工猜测替代。逐条核对：圆线在偏高时直径增加、偏低时直径减小；扁线或箔材在偏高时仅为同厚加宽或同宽加厚，偏低时仅为相反方向；任何记录必须是同一导线类别下的真实完整目录项。报告应同时给出每方向尝试数、不可计算数、改善数及回退普通随机变异数。

### 4.5 命令行消融功能回归（本轮必须执行）

配置 445 已做过一轮功能复测；若本轮之后未改 `main.py`、`ga/full_optimizer.py`、`ga/optimizer_runtime.py` 或轨迹结构，则无需机械重复。若这些文件再次改动，使用小演化预算做回归：

```powershell
& C:\ProgramData\anaconda3\envs\python310\python.exe main.py ga-ablation `
  --config-id 445 `
  --seeds 20260918,20260919 `
  --evolution-evaluation-budget 100
```

需检查四种策略 `baseline`、`coupled`、`empirical_injection`、`guided_mutation` 的 `settings_json` 与来源计数；每次运行必须生成唯一 SQLite 文件；`evolution_evaluations` 达到 B′ 后立即停止；缓存命中不计为真实精算；精英复制不能被误记为新的交叉或变异动作。另需核对每条运行和批次汇总都保存非负耗时、公式版本、核心代码指纹、入口和策略，且同一批次的公式版本/代码指纹一致。

## 5. 轨迹回放与页面可用性

### 5.1 待验证结论

1. 70 MB 及更大的轨迹进入“轨迹回放”时不会因自动解析全量候选而长时间白屏。
2. 第 0 代预览轨迹和完整 GA 轨迹显示不同的可用视图，不把未执行的父代/档案信息伪装为未知数据。
3. 候选详情中的中文结构、约束、来源、本代去向和档案归属足以解释一条候选，不必默认阅读 JSON。

### 5.2 如何测试

1. 选取现有的大文件轨迹，例如 `outputs/ga-run-401-20260918.sqlite3`、`ga-run-415-20260919.sqlite3` 或 `ga-run-497-20260920.sqlite3`。
2. 进入轨迹回放页，记录首次进入页面到出现文件选择控件的时间；此时不点击“加载选定轨迹”。
3. 选择文件并点击加载，记录摘要加载时间；再进入候选明细，记录首次候选级解析时间。
4. 切换运行概览、代际过程、候选与演化关系、实验设置，确认已加载摘要不会反复全量解析。
5. 再加载一份 `initial-preview` 轨迹，确认其只出现“第 0 代概览 / 候选与精算结果 / 本次预览设置”。

### 5.3 报告必须包含

- 文件名、文件大小、浏览器/机器环境；

## 6. 正式多种子效果实验

### 6.1 仍需验证的核心结论

已有配置 401、v8、B′=8000、20 个配对种子的历史实验：经验有效域注入在该批次中有改善；耦合交叉和定向变异未检出额外收益；401 的油道域没有可动邻居，无法检验油道优先。当前代码与该批次的公式版本和局部搜索细节不同，不能把上述现象直接写成当前代码结论。以下结论仍须靠**当前版本**的多随机种子实验获得：

1. 结构电磁耦合交叉是否提高在固定演化成本内得到严格解的概率；
2. 经验有效域随机注入是否优于只从原始域随机生成候选；
3. 诊断反馈变异是否改善首次严格解、最小近可行超限或严格成本；
4. 阻抗油道优先规则是否比原来的铁芯优先更有效，还是只在某些配置生效。

### 6.2 先做 5 个配对种子排练

目的不是公布优劣，而是先确认当前版本的主配置能产生可解释的结果、记录公式版本和工作种群筛选效果、选择正式 B′、估算耗时和磁盘占用，并确认轨迹中的字段足够统计。

建议当前定位：401 可优先作为主配置候选；415 可作中性参照；497 有较强历史种子条件，应单独解释；445 如在选定 B′ 内仍没有严格解，只能用于近可行过程研究，不能作为严格成本主实验。

操作要求：

1. 固定一个配置、一个完整搜索域、一个程序版本和同一批 5 个随机种子；
2. 先选择一个候选演化预算 B′，对同一批种子的所有策略完全一致地执行；
3. 每个种子依次运行 `baseline`、`coupled`、`empirical_injection`、`guided_mutation`；
4. 若排练后要改变 B′，应以新 B′ 重跑整批 5 个种子，不能把不同 B′ 的结果混成一组；
5. 第 0 代成本单列报告，不计入 B′；正常页面运行不需要也不应强制填写预算。

### 6.3 再做正式实验

在 5 种子排练后，固定配置、搜索域、程序版本、B′ 与种子列表，至少 10 个、目标 20 个配对种子。每个种子四种策略均运行一次，并保留独立 SQLite、批次 `manifest.json` 与 `summary.csv`。

统计前必须核对：配置 ID、搜索域指纹、精算器版本、策略设置、B′ 和种子完全一致。任何一项不同的运行不得放入同一张主统计表。

### 6.4 效果实验报告必须包含

| 层级 | 必填内容 |
| --- | --- |
| 实验输入 | 配置 ID、搜索域、程序版本、B′、种子列表、四种策略的实际 settings。 |
| 资源 | 每次运行的第 0 代调用、演化调用、总耗时、SQLite 大小、停止原因。 |
| 严格解 | 每策略在 B′ 内的严格解种子数/比例；每个种子的首次严格解演化调用和最佳严格成本。 |
| 无严格解 | 每策略每个种子的最小近可行总超限、最大超限和违规数量。 |
| 配对比较 | 同一随机种子下策略之间的结果差，不只给总体平均值。 |
| 定向变异过程 | 按主导违规、违规方向、实际探测模块和动作汇总尝试数、改善数、进入严格域数和真实精算调用。 |
| 结论边界 | 明确结论只覆盖当前配置/搜索域/B′；没有严格解时不比较严格成本。 |

正式统计可报告严格解成功数、严格成本中位数/IQR、首次严格解调用数、最小近可行超限、耗时和缓存命中。若双方均没有严格解，只报告近可行指标，并写明“可行性尚未建立”。不能从“入档前最后动作”直接推导某个算子的因果贡献。
